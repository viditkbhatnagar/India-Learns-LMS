# ADR 0003 — No payment gateway in Phase 1

**Status:** Accepted
**Date:** 2026-02-01 (locked in `01_BRD.md` §6)
**Author:** Logan (LUC), Vidit Bhatnagar

## Context

LUC's Phase 1 fee operation is offline — students pay LUC directly via UPI, bank transfer, cheque, or cash, and LUC's finance team records each payment. The platform needs to track who has paid what, generate receipts, and communicate fee status to students. We considered three options:

1. **Integrate a payment gateway** (Razorpay / PhonePe / Cashfree) so students pay through the platform.
2. **No gateway; record payments manually.**
3. **Both** — manual recording today, gateway later as Phase 2.

## Decision

**No payment gateway in Phase 1.** Finance staff record payments manually via the platform. Receipts are PDF-generated by `pdfkit` server-side, stored in Cloudinary, and downloadable via TTL-bounded signed URLs.

Phase 1 supports payment **methods** (cash, cheque, bank transfer, UPI, other) as a string enum on the `Payment` record, but no money flows through the platform.

## Rationale

- **LUC's existing process is offline.** Adding a gateway changes business process, training, and reconciliation; that's a separate engagement.
- **Compliance load.** A payment gateway brings PCI-DSS scope, KYC requirements, and a richer privacy posture. Manual recording keeps Phase 1 outside PCI scope entirely (we never see card data).
- **Smaller blast radius.** A bug in payment recording is correctable via reversal + re-record. A bug in a live gateway integration could be a money problem.
- **Faster shipping.** Phase 1 needs to be ready for June internal test and July full launch — adding a gateway adds weeks.

## Consequences

**Good:**

- No card data on our infrastructure.
- No PCI-DSS audit obligation.
- Payments and receipts are still fully traceable on the platform.
- Reversals leave audit + credit-note trails — clean accounting.

**Trade-offs:**

- Students cannot pay through the platform — they pay LUC out of band, then wait for finance to record.
- Manual recording means a 24-hour latency between payment and platform reflection. Documented in [user-guides/student-handbook.md](../../user-guides/student-handbook.md) FAQ.
- Reconciliation between bank statements and platform records is a finance team task, not platform-automated.

## Alternatives considered

- **Razorpay integration.** Mature India-focused gateway, but adds vendor risk + PCI scope.
- **PhonePe / UPI direct.** Even lighter, but UPI-only excludes cheque payers and corporate-tuition flows.
- **Pluggable interface now, integration later.** The current `paymentService` is already a clean service boundary — when we add a gateway in Phase 2, the touch points are the routes, not the model.

## Phase 2 roadmap

- Pick a gateway based on cohort size and LUC's reconciliation needs.
- Add a `paymentGateway` field to `Payment` with provider + provider-id.
- Add a webhook receiver under `/v1/jobs/` (HMAC-signed, idempotent).
- Update [refund-policy.md](../../legal/refund-policy.md) and [vendor-risk-register.md](../../compliance/vendor-risk-register.md).
