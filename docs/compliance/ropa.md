# Records of Processing Activities (RoPA)

A **Record of Processing Activity** is a structured description of every distinct purpose for which India Learns processes personal data. Although the DPDP Act 2023 does not yet prescribe a fixed RoPA template, this format follows the EU Article 30 model, which is widely adopted and gives any auditor a familiar entry point.

The columns are: **Activity • Purpose • Data Principals • Data Categories • Source • Recipients • International transfers • Retention • Security measures**.

The unit of analysis is a *processing activity*, not a feature. Multiple features may belong to the same activity if they share the same purpose and data flow.

## A1. Identity and account lifecycle

| Field | Value |
|---|---|
| **Activity** | Create, maintain, and decommission user accounts (student, faculty, admin, finance, superadmin) |
| **Purpose** | Identify and authenticate users; enforce role-based access; record account state changes for accountability |
| **Data principals** | Students, faculty, LUC admin staff, LUC finance staff, vendor superadmin |
| **Data categories** | Name, email, phone (E.164), address, role, programme/batch link, account status, password hash + history, last-login timestamp, lockout counters, soft-delete flag |
| **Source** | LUC enrolment record (offline) → admin invitation → user-supplied at first login |
| **Recipients (internal)** | LUC admins, vendor support |
| **Recipients (external)** | None — identity data does not leave the service except as part of audit-log queries by authorised reviewers |
| **International transfers** | None |
| **Retention** | While account is active + 90 days after revocation (soft-delete), then hard delete unless held under legitimate-interest hold (litigation, regulatory). See [data-retention-policy.md](data-retention-policy.md) |
| **Security** | Argon2id passwords; JWT access; rotated refresh tokens; rate-limited login; audit on every change. See [../security/cryptography.md](../security/cryptography.md) and [../security/access-control.md](../security/access-control.md) |
| **Code references** | [`api/src/models/user.ts`](../../api/src/models/user.ts), [`authService.ts`](../../api/src/services/authService.ts), [`userService.ts`](../../api/src/services/userService.ts) |

## A2. Authentication and session management

| Field | Value |
|---|---|
| **Activity** | Issue and verify access tokens; manage refresh-token families; enforce session caps |
| **Purpose** | Securely identify the bearer of a request and prevent session hijacking |
| **Data principals** | All authenticated users |
| **Data categories** | Token hashes (SHA-256), `familyId`, `deviceId`, IP address, user agent, lifecycle timestamps |
| **Source** | Generated by the API; the device id is the cookie identifier |
| **Recipients (internal)** | The API itself; admins reviewing audit logs |
| **Recipients (external)** | None |
| **International transfers** | None |
| **Retention** | Until the refresh token's `expiresAt` (default 14 days) + 30 days for forensic context, then deleted by retention sweep (planned) |
| **Security** | Plaintext tokens never stored; cookies use `__Host-` prefix |
| **Code references** | [`refreshTokenService.ts`](../../api/src/services/refreshTokenService.ts), [`models/refreshToken.ts`](../../api/src/models/refreshToken.ts) |

## Adding a new activity

When you ship a feature that introduces a new processing activity:

1. Add a new section here with the same fields.
2. Update [data-classification.md](data-classification.md) if it brings in a new category of data.
3. Update [data-retention-policy.md](data-retention-policy.md) with the retention.
4. If a new subprocessor is introduced, add it to [vendor-risk-register.md](vendor-risk-register.md).
5. Update [../legal/privacy-policy.md](../legal/privacy-policy.md) if any of the above is user-visible.
